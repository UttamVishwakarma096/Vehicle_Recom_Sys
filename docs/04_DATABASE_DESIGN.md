# MongoDB Database Design

**Product:** Smart Vehicle Recommendation System  
**Status:** Draft for review  
**Source documents:** `01_PRD.md`, `02_REQUIREMENTS.md`,
`03_SYSTEM_ARCHITECTURE.md`  
**Version:** 1.0

## 1. Data ownership principles

This design follows the approved three-service split. Each service owns
its MongoDB database and is the only service permitted to read or write
that database's collections. Services exchange identifiers and data
through versioned APIs, not cross-service MongoDB queries or Mongoose
population.

| Service | Logical database | Owned collections |
|---|---|---|
| Identity and User Service | `vehicle_identity` | `users` |
| Vehicle Catalog Service | `vehicle_catalog` | `vehicles`, optional `admin_audit_logs` |
| Recommendation Service | `vehicle_recommendations` | `favorites`, optional `recommendation_history` |

Logical databases may share a MongoDB Atlas cluster if deployment
requires it, but each service must use separate least-privilege
credentials restricted to its own database. Separate physical clusters
are a deployment choice, not a requirement of this logical design.

No MongoDB collection, database reference, or transaction is shared
between services. A `userId` or `vehicleId` stored outside its owning
service is an opaque external identifier (string form of the owning
service's ID), not a local Mongoose reference.

## 2. Shared data conventions

- MongoDB `_id` uses `ObjectId` for records owned by the service.
- Cross-service IDs are stored as strings and validated through the
  owning service's API when the operation requires current data.
- Timestamps use BSON `Date` values in UTC. Mongoose `timestamps` may
  manage `createdAt` and `updatedAt`.
- API JSON uses lower camel case and serializes IDs as strings.
- Vehicle prices are stored as `Decimal128` to avoid binary
  floating-point currency arithmetic.
- Currency is `INR` for the initial scope. Price type distinguishes
  `ex_showroom`, `on_road`, and `used`.
- Absent or unknown specifications are omitted or explicitly represented
  using the selected API contract; they are never replaced with
  invented values.
- User secrets, JWTs, raw tokens, and ML credentials are never stored in
  catalog or recommendation records.
- Schema validation occurs both at the API/service boundary and at
  persistence where feasible.

## 3. Identity and User Service database

### 3.1 `users`

**Purpose:** Account authentication, role enforcement, user profile,
and saved recommendation preferences.

| Field | Type | Required | Rules / default |
|---|---|---:|---|
| `_id` | ObjectId | Yes | Generated by MongoDB |
| `email` | String | Yes | Trimmed, normalized lowercase, valid email syntax; unique index |
| `passwordHash` | String | Yes | Adaptive salted hash only; never returned by API |
| `role` | String enum | Yes | `user` or `admin`; default `user`; never client-editable |
| `profile.displayName` | String | No | Trimmed; length limit defined by API validation |
| `profile.city` | String | No | Optional; no inferred location |
| `preferences.budget.min` | Decimal128 | No | Non-negative INR amount |
| `preferences.budget.max` | Decimal128 | No | Non-negative INR amount; not less than min |
| `preferences.budget.priceType` | String enum | No | `ex_showroom`, `on_road`, or `used`; required when saving budget bounds |
| `preferences.vehicleTypes` | Array of strings | No | Allowlisted body type values |
| `preferences.fuelTypes` | Array of strings | No | Allowlisted values |
| `preferences.transmissions` | Array of strings | No | Allowlisted values |
| `preferences.minimumSeats` | Integer | No | Positive supported seat count |
| `preferences.drivingEnvironment` | String enum | No | Approved values, e.g. city/highway/mixed |
| `preferences.annualDistanceKm` | Number | No | Finite and non-negative |
| `preferences.priorities.reliability` | Number | No | Finite, normalized to approved range |
| `preferences.priorities.maintenanceCost` | Number | No | Finite, normalized to approved range |
| `preferences.priorities.fuelEfficiency` | Number | No | Finite, normalized to approved range |
| `preferences.priorities.safety` | Number | No | Finite, normalized to approved range |
| `preferences.priorities.performance` | Number | No | Finite, normalized to approved range |
| `createdAt` | Date | Yes | Generated on creation |
| `updatedAt` | Date | Yes | Updated on each mutation |

Priority scales, allowed body/fuel/transmission values, email
verification, password policy, and profile-editable fields must be
finalized in the API/security design before implementation. Empty
preference objects are valid; missing preferences must not be silently
filled with arbitrary values.

#### Validation and access control

- Normalize email before uniqueness checks.
- Never accept `role`, `_id`, `passwordHash`, or timestamps from a
  profile update.
- Hash passwords before persistence and use a generic credential error
  at login.
- Profile and preference operations use the authenticated subject from
  verified identity, not an arbitrary client `userId`.
- Service APIs return a safe user projection that excludes
  `passwordHash`.
- Do not log password or authentication credential values.

#### Indexes

| Index | Type | Justification |
|---|---|---|
| `{ email: 1 }` | Unique | Prevent duplicate normalized accounts and support login lookup |

No index is proposed on free-form profile or preference fields until
query patterns demonstrate a need; user preferences are fetched by user
identity, not used as a global search index.

#### Example valid document

```json
{
  "_id": "665000000000000000000001",
  "email": "sample.user@example.test",
  "passwordHash": "<adaptive-hash-placeholder>",
  "role": "user",
  "profile": {
    "displayName": "Sample User"
  },
  "preferences": {},
  "createdAt": "2026-01-01T00:00:00.000Z",
  "updatedAt": "2026-01-01T00:00:00.000Z"
}
```

This is a schema illustration only; the hash placeholder is not a
credential.

#### Expected query patterns

- Login: exact normalized email lookup.
- Current profile/preferences: exact `_id` lookup from verified
  identity.
- Admin user operations, if later approved: paginated by creation date
  or email; not a public endpoint.

## 4. Vehicle Catalog Service database

### 4.1 `vehicles`

**Purpose:** Source of truth for catalog specifications, prices,
publication state, and data provenance.

| Field | Type | Required | Rules / default |
|---|---|---:|---|
| `_id` | ObjectId | Yes | Generated by MongoDB; exposed as an opaque vehicle ID |
| `make` | String | Yes | Trimmed, non-empty |
| `model` | String | Yes | Trimmed, non-empty |
| `modelYear` | Integer | No | Validated against product policy; no assumed year when absent |
| `variant` | String | No | Trimmed if supplied |
| `bodyType` | String enum | No | Allowlisted supported value |
| `fuelType` | String enum | No | Allowlisted supported value |
| `transmission` | String enum | No | Allowlisted supported value |
| `seatingCapacity` | Integer | No | Positive integer if known |
| `specifications.engine` | Mixed/object | No | Only verified fields with units; schema to be finalized with source |
| `specifications.power` | Mixed/object | No | Value/unit only when available and verified |
| `specifications.claimedMileage` | Object | No | `value`, `unit`, and provenance; not an independent measurement |
| `specifications.measuredMileage` | Object | No | Observation value/unit and observation provenance; not manufacturer claim |
| `prices` | Array of price objects | No | May contain distinct price types and dates; must not conflate price categories |
| `status` | String enum | Yes | `draft`, `published`, or `unpublished`; default `draft` |
| `dataSources` | Array of source objects | No | Provenance fields for source, source record, license/terms reference, retrieval time |
| `verifiedAt` | Date | No | Time the entry or supported fields were verified; not auto-set without verification |
| `verifiedBy` | String | No | Opaque admin user ID from Identity Service, not a MongoDB reference |
| `createdBy` | String | Yes | Opaque admin user ID from Identity Service |
| `updatedBy` | String | No | Opaque admin user ID from Identity Service |
| `createdAt` | Date | Yes | Generated on creation |
| `updatedAt` | Date | Yes | Updated on mutation |

Price object:

| Field | Type | Required | Rules |
|---|---|---:|---|
| `type` | String enum | Yes | `ex_showroom`, `on_road`, or `used` |
| `amount` | Decimal128 | Yes | Greater than zero; no inferred or synthetic production price |
| `currency` | String enum | Yes | `INR` for initial product scope |
| `effectiveAt` | Date | No | When the price applies, if supplied |
| `sourceId` | String | No | Identifies applicable entry in `dataSources` |
| `verifiedAt` | Date | No | Price-specific verification timestamp |

Each price record is independent. A used price may need year, mileage,
condition, and location attributes; those requirements depend on
approved used-vehicle catalog scope and must be defined before enabling
such listings.

Provenance object:

| Field | Type | Required | Rules |
|---|---|---:|---|
| `provider` | String | Yes | Human-readable source/provider label |
| `sourceRecordId` | String | No | Source-side record key where available |
| `sourceUrl` | String | No | Valid URL when permitted; do not expose restricted URLs |
| `licenseReference` | String | No | Reference to approved data terms |
| `retrievedAt` | Date | Yes | UTC retrieval/import time |
| `fieldPaths` | Array of strings | No | Catalog paths supported by this source record |

#### Validation and access control

- Public listing/detail APIs query `status: "published"` only.
- Only an authorized administrator can create, edit, publish, unpublish,
  or delete records.
- The Catalog Service verifies administrator identity using the
  approved token policy; a request body role is never trusted.
- Validate each price's amount, currency, type, and source association.
- A missing field is not replaced with an estimated/typical value.
- `claimedMileage` and `measuredMileage` are distinct; measured
  observations require appropriate source/context.
- Catalog specifications, user observations, maintenance history, and
  model labels remain distinct concepts.
- Do not publish fields whose source/license terms prohibit display.

#### Indexes

| Index | Type | Justification |
|---|---|---|
| `{ status: 1, make: 1, model: 1, modelYear: -1 }` | Compound | Public/admin catalog filtering and stable make/model browsing |
| `{ status: 1, bodyType: 1, fuelType: 1, transmission: 1 }` | Compound | Common supported filter combination; confirm against query measurements |
| `{ status: 1, "prices.type": 1, "prices.amount": 1 }` | Compound/multikey as supported | Budget filtering by a specific price type; verify query plan and MongoDB index constraints |

Text search implementation (MongoDB text index or another approved
search strategy) is intentionally not fixed until search fields,
language behavior, and query patterns are approved. Index usage and
compound index order must be validated against representative,
non-production data.

#### Example valid document

```json
{
  "_id": "665000000000000000000101",
  "make": "SAMPLE ONLY - NOT REAL",
  "model": "DEMO RECORD",
  "status": "draft",
  "createdBy": "665000000000000000000001",
  "dataSources": [],
  "createdAt": "2026-01-01T00:00:00.000Z",
  "updatedAt": "2026-01-01T00:00:00.000Z"
}
```

This synthetic draft illustrates that a record may exist without
invented specifications or price and is not a real vehicle listing.

#### Expected query patterns

- Public listing: `status`, supported filters, price type/range,
  deterministic sort, and pagination.
- Public details: exact `_id` plus `status: "published"`.
- Admin catalog: paginated by publication status, make/model, and
  update/verification date.
- Import/quality review: filter by source, verification state, and
  stale/missing provenance.

### 4.2 Optional `admin_audit_logs`

**Purpose:** Record privileged catalog mutations if the approved
operational, privacy, and retention policy requires an audit trail.
This collection is not a substitute for application logs.

| Field | Type | Required | Rules |
|---|---|---:|---|
| `_id` | ObjectId | Yes | Generated |
| `actorUserId` | String | Yes | Opaque Identity Service user ID |
| `action` | String enum | Yes | `create`, `update`, `publish`, `unpublish`, `delete` |
| `vehicleId` | String | Yes | Opaque Catalog Service vehicle ID |
| `changedFields` | Array of strings | No | Field names only by default; avoid duplicating full sensitive values |
| `correlationId` | String | No | Request correlation identifier |
| `createdAt` | Date | Yes | UTC event time |

**Access:** Catalog administrators with audit permission only; never
public. Define retention and immutability requirements before enabling.

**Indexes:** `{ vehicleId: 1, createdAt: -1 }` and
`{ actorUserId: 1, createdAt: -1 }` for audit lookup.

**Example:**

```json
{
  "_id": "665000000000000000000102",
  "actorUserId": "665000000000000000000001",
  "action": "update",
  "vehicleId": "665000000000000000000101",
  "changedFields": ["status"],
  "createdAt": "2026-01-01T00:00:00.000Z"
}
```

The example is illustrative; enable this collection only after audit
policy approval.

## 5. Recommendation Service database

### 5.1 `favorites`

**Purpose:** Store each user's saved vehicle relationships. It does not
own vehicle specifications or user identity records.

| Field | Type | Required | Rules / default |
|---|---|---:|---|
| `_id` | ObjectId | Yes | Generated by MongoDB |
| `userId` | String | Yes | Opaque Identity Service ID, derived from verified credential |
| `vehicleId` | String | Yes | Opaque Catalog Service ID, validated through Catalog API on create |
| `createdAt` | Date | Yes | UTC timestamp |
| `updatedAt` | Date | Yes | UTC timestamp |

The current vehicle details are fetched from the Catalog Service when
needed. If a minimal display snapshot is later approved for availability
or historical display, it must be explicitly non-authoritative, contain
only allowlisted fields, and identify its capture time.

#### Validation and access control

- Ownership is always derived from verified identity, never accepted as
  an arbitrary client-selected `userId`.
- The Recommendation Service must verify the vehicle is currently
  publishable before creating a favorite.
- When listing favorites, stale/unpublished/missing catalog records
  produce a safe unavailable state; the service must not fabricate
  vehicle details.
- Removing a favorite only affects the authenticated user's matching
  record.

#### Indexes

| Index | Type | Justification |
|---|---|---|
| `{ userId: 1, vehicleId: 1 }` | Unique compound | Prevent duplicate favorite per user/vehicle |
| `{ userId: 1, createdAt: -1 }` | Compound | Efficient user's favorite list in saved order |
| `{ vehicleId: 1 }` | Non-unique | Catalog reference cleanup/reporting if needed; retain only if query patterns justify it |

#### Example valid document

```json
{
  "_id": "665000000000000000000201",
  "userId": "665000000000000000000001",
  "vehicleId": "665000000000000000000101",
  "createdAt": "2026-01-01T00:00:00.000Z",
  "updatedAt": "2026-01-01T00:00:00.000Z"
}
```

IDs above are illustrative and do not indicate real accounts or catalog
entries.

#### Expected query patterns

- List favorites by authenticated `userId`, newest first, paginated.
- Add/remove by `(userId, vehicleId)`.
- Optional reference cleanup/reporting by `vehicleId`; do not use
  direct catalog database access.

### 5.2 Optional `recommendation_history`

**Purpose:** Store a user's submitted preferences and result summary
only if product approval, privacy policy, and retention requirements
enable recommendation history.

| Field | Type | Required | Rules |
|---|---|---:|---|
| `_id` | ObjectId | Yes | Generated |
| `userId` | String | Yes | Opaque Identity Service ID from verified credential |
| `ruleVersion` | String | Yes | Exact deterministic recommendation rules version |
| `preferencesSnapshot` | Object | Yes | Validated submitted preferences; minimize personal data |
| `results` | Array | Yes | Ordered opaque vehicle IDs, scores, and explanation codes; no copied catalog truth |
| `createdAt` | Date | Yes | UTC timestamp |
| `expiresAt` | Date | No | Required if retention uses TTL; policy-controlled |

**Access:** The owner only. Store nothing if history is disabled or
retention approval is absent. A catalog update can change current
vehicle data; stored results are historical summaries, not current
catalog truth.

**Indexes:**

- `{ userId: 1, createdAt: -1 }` for the user's history.
- Optional TTL index on `expiresAt` only after an explicit retention
  duration and deletion policy are approved.

**Example document (illustrative, history feature disabled by default):**

```json
{
  "_id": "665000000000000000000202",
  "userId": "665000000000000000000001",
  "ruleVersion": "rules-v1",
  "preferencesSnapshot": {
    "budget": {
      "min": "500000",
      "max": "1000000",
      "currency": "INR",
      "priceType": "ex_showroom"
    }
  },
  "results": [],
  "createdAt": "2026-01-01T00:00:00.000Z"
}
```

The amounts are synthetic placeholders for schema illustration, not
vehicle prices or market data.

## 6. Longevity and ML data boundaries

No training dataset, target labels, maintenance history, or model
outcomes are supplied by the project prompt. Do not seed invented
longevity labels or represent catalog fields as sufficient evidence.

If an approved ML program later needs persistent training/evaluation
data, define a separate data owner, permission and consent basis,
provenance, target semantics, retention, and access policy first. Do not
place those records in `vehicles` or expose them through public catalog
APIs.

The initial databases therefore contain no model training labels,
predicted lifetime, repair outcome, or unapproved prediction fields.
Model artifacts and version metadata belong to the ML service's
approved artifact store/configuration, not user-controlled MongoDB
fields.

## 7. Cross-service references and consistency behavior

| Reference | Owner | Stored by | Validation/use |
|---|---|---|---|
| User ID | Identity Service | Recommendation favorites/history; Catalog audit | Opaque string from verified token; API validation when current account status is needed |
| Vehicle ID | Catalog Service | Recommendation favorites/history | Opaque string; Catalog API validation for create/display |
| Admin actor ID | Identity Service | Catalog audit | Opaque string from verified admin identity |

- No foreign-key cascade is available across service databases.
- Account deletion must be coordinated through approved service APIs or
  a documented workflow; no direct cross-service delete is allowed.
- Catalog unpublish/delete must not make a favorite endpoint leak
  hidden catalog information.
- Synchronous cross-service calls can fail. Each caller must use
  timeouts and return an explicit safe degraded/error result.
- The system does not assume distributed transactions. Any future
  event-driven propagation requires a separately approved architecture.

## 8. Data retention, deletion, and backup

- User account, profile, and saved preference retention/deletion need an
  approved privacy policy.
- Favorites should be deleted when a user removes them; full account
  deletion requires coordinated cleanup across Identity and
  Recommendation services.
- Recommendation history is disabled by default until retention and
  deletion are approved.
- Audit-log retention and immutability are undecided; do not enable the
  optional audit collection until policy approval.
- Production backup, encryption, recovery-point, and restore procedures
  must be selected for the MongoDB hosting plan and tested. Never use a
  production database for destructive tests.

## 9. Unresolved schema decisions

1. Exact catalog source, licensing, market/geographic scope, and refresh
   process.
2. Supported price comparison policy and used-vehicle data shape.
3. Controlled vocabulary for body type, fuel, transmission, environment,
   and specification units.
4. Whether email verification, password reset, and refresh-token
   revocation require additional identity collections.
5. Whether user profile supports city or other optional data, and
   associated privacy/retention policy.
6. Recommendation priority scale, weight mapping, missing-data policy,
   and rule-version configuration lifecycle.
7. Whether favorite snapshots or recommendation history are required.
8. Whether administrator audit logs are required and for how long they
   are retained.
9. Production MongoDB hosting and whether services use their own logical
   databases on a shared cluster or separate physical clusters.
10. Whether future ML training data exists, is authorized, and has a
    trustworthy outcome label.

## 10. Review gate

This database design follows the approved three-service ownership
boundaries and does not implement any data access. Approve the service
schemas, optional collections, index plan, and unresolved retention/data
decisions before finalizing the API specification.

**Database provider decision:** Use MongoDB Atlas with the three logical
databases listed above and a distinct database-scoped credential for
each service. Recommendation history and catalog audit collections
remain disabled. The Atlas cluster topology and operational settings
remain to be configured.
